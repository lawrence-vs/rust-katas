# 233 advanced: one Rust type, two checked contracts

**Concept:** one Rust type is the source of three artifacts: the JSON wire shape (serde), the OpenAPI 3.1 document for REST (3.1 reuses JSON Schema, so `schemars` output drops into `components.schemas`) and a protobuf message in a checked-in `.proto` file. Tests fail when the type and the checked-in contracts disagree, so drift shows in CI, not in a client. OpenAPI covers HTTP only; a WebSocket feed needs AsyncAPI, out of scope here.
**Source:** kraken-cli (MIT) generates and checks in `agents/tool-catalog.json`, whose `input_schema` comes from the command's Rust type via schemars, regenerated by `just catalog` and checked by `crates/kraken-cli/tests/mcp_surface.rs:293`. kraken-cli has no OpenAPI or gRPC; the pattern is the generated-and-checked catalog, and this kata extends it to OpenAPI and protobuf. https://spec.openapis.org/oas/v3.1.0 ; https://protobuf.dev/programming-guides/proto3/ ; https://docs.rs/schemars/latest/schemars/
**Fails with:** `openapi and rust disagree on field names`
**Vault:** your note on contract-first vs code-first API design

## Task
Make `cargo test` pass. Edit `src/lib.rs` only; `contract/orders.proto`, `contract/openapi.json` and `tests/kata.rs` must not change. The checked-in OpenAPI document is the spec a generator would build a client from; it is regenerated from the type, never edited by hand. Keep one source of truth: the Rust field name is the wire name. Do not hand-write the OpenAPI schema; keep it generated by schemars.

## Related concepts
### `utoipa`
Code-first OpenAPI: derive a schema from the type and collect paths with macros. Use it when you want the whole document, not just schemas, generated.
```rust
#[derive(utoipa::ToSchema)]
struct Quote { bid: u32 }
```

### `prost`
Generates Rust structs from `.proto` files at build time (the opposite direction). Use it when the proto is the source of truth.
```rust
// build.rs
prost_build::compile_protos(&["quote.proto"], &["."])?;
```

### AsyncAPI
OpenAPI's counterpart for message-based and WebSocket APIs. Use it to describe channels and events that HTTP paths cannot.
```yaml
asyncapi: 3.0.0
channels:
  ticker: { address: ticker }
```
